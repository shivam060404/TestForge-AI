# Design Document: UX / UI / Frontend System

## 1. Design Vision

The frontend should feel like a **QA mission control cockpit**:
- clear
- trustworthy
- explainable
- evidence-rich
- developer-friendly
- low-noise but highly informative

The product must communicate:
- what the agent did
- why it did it
- what failed
- how it healed
- what design issues were detected
- what needs human approval

---

# 4. Design System

## Visual Language
- clean enterprise developer tool aesthetic
- high readability
- subtle borders
- strong status colors
- dense but not cluttered

## Color Tokens
- background: neutral light/dark
- surface: elevated cards
- primary: indigo/blue
- success: green
- warning: amber
- danger: red
- info: cyan

## Typography
- Inter or Geist
- strong hierarchy
- monospace for selectors/logs

## Components
Use shadcn/ui components:
- Button
- Badge
- Card
- Table
- Tabs
- Dialog
- Drawer
- Toast
- Skeleton
- Progress
- Tooltip
- Switch
- Select

---

# 5. Key Interaction Patterns

## Live Run Streaming
- use SSE
- update timeline in real time
- show spinner/skeleton for pending steps
- show evidence thumbnails immediately

## Healing Approval Flow
- candidate opens in drawer
- side-by-side old/new comparison
- confidence meter
- approve triggers optimistic update + API call
- toast confirms result

## Visual Diff Viewer
- slider-based before/after compare
- bounding box overlay for changed regions
- zoom controls

---

# 6. State Management

## Server State
- TanStack Query
- cache invalidation on mutations

## Client State
- Zustand for:
  - selected run
  - live event buffer
  - UI filters
  - diff viewer state

---

# 7. Empty / Loading / Error States

Every screen must define:
- empty state
- loading state
- partial error state
- fatal error state

### Examples
- no test cases yet → CTA to create first test
- run failed due to environment → show retry and diagnostics
- healing queue empty → show success state

---

# 8. Accessibility Requirements

The QA product itself must be accessible:
- keyboard navigation
- focus states
- proper labels
- aria-live for run updates
- color contrast compliance
- reduced motion support

# 9. Frontend Data Model

## Types
```ts
type RunStatus =
  | "QUEUED"
  | "PLANNING"
  | "EXECUTING"
  | "VERIFYING"
  | "HEALING"
  | "COMPLETED"
  | "FAILED"
  | "NEEDS_APPROVAL";

type StepExecution = {
  id: string;
  stepId: string;
  status: "PENDING" | "RUNNING" | "PASSED" | "FAILED" | "HEALED";
  errorMessage?: string;
  screenshotUrl?: string;
  durationMs?: number;
};

type HealingCandidate = {
  id: string;
  runId: string;
  type: "LOCATOR" | "TIMING" | "ACTION";
  oldValue: string;
  newValue: string;
  confidence: number;
  status: "PENDING" | "APPROVED" | "REJECTED" | "AUTO_APPLIED";
};

type DesignInsight = {
  id: string;
  type: "VISUAL" | "ACCESSIBILITY" | "LAYOUT";
  severity: "LOW" | "MEDIUM" | "HIGH";
  description: string;
  screenshotUrl?: string;
};
